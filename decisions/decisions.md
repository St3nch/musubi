# Musubi Decisions

These are accepted Product/project decisions for Musubi. They do not become authority inside another VedaOps project merely because Musubi records them.

## D1 — Musubi reads truth and writes possibility

Musubi reads native authority and writes institutional memory, discovery, interpretation, ideas, lessons, signals, and suggestions.

It does not become a synchronized second representation of project truth.

## D2 — Projects remain independently authoritative

Each project owns its Product doctrine, accepted project decisions, implementation, code, project-local deferrals, runtime state where applicable, and project-local history.

Projects must function correctly without Musubi.

## D3 — Musubi has read-only project access

The Musubi reasoner may inspect authorized project repositories and other native sources for current truth.

It does not receive project-write authority.

## D4 — Musubi uses a separate institutional reasoner

The primary Musubi consumer is a separate LLM/agent optimized for institutional context recovery, cross-project reasoning, idea discovery, and suggestion.

It is not a project writer.

## D5 — CHAZ is the decision boundary

Musubi suggestions do not authorize project work.

Project work begins only after explicit Product judgment and the affected project's normal governed process.

## D6 — Normal Musubi chat is read-only

Ordinary conversational use must not mutate durable Musubi state.

## D7 — Musubi writes are preview-before-write

When write mode is enabled, the reasoner prepares the exact proposed mutation and shows it to CHAZ before any durable write.

CHAZ may approve, reject, or request revision.

## D8 — Candidate and curated knowledge remain distinct

Project agents and the Musubi reasoner may propose candidate institutional knowledge.

Candidate material does not become part of the default curated Musubi corpus without CHAZ / Steward review.

No complex workflow engine is required for the initial model.

## D9 — Retained, believed, decided, and authorized are not synonyms

Musubi must preserve the difference between retaining an idea, believing a conclusion, making an institutional decision, and authorizing project work.

## D10 — Musubi retains institutional value added, not project mirrors

Detailed capability inventories, implementation state, runtime state, project-local queues, and project-local deferral registers remain native.

Musubi retains cross-project value, institutional rationale, useful history, lessons, signals, relationships, ideas, suggestions, and minimal authority pointers.

## D11 — Project representation begins minimal

A Project entry needs only stable identity, useful naming, one-sentence orientation, and authority access unless real institutional context justifies more.

No lifecycle or development-posture enum is accepted for the initial prototype.

## D12 — Exact source revision is selective observation, not verification

A Git revision may be retained when useful to identify the project state observed while developing a source-dependent Musubi note.

It is not a universal reconciliation cursor or semantic certificate.

## D13 — Markdown + Git remains the initial durable substrate

Musubi begins as portable Markdown under version control.

Search/vector/graph systems may be added later as rebuildable derivatives when measured pressure requires them.

## D14 — Suggestions should preserve basis and limits

Consequential suggestions should identify why they matter now, source basis, Musubi inference, assumptions/limits, material counterevidence, and the consideration being requested from CHAZ.

## D15 — Idea generation is conservative by default

Musubi optimizes for useful interruption rate rather than idea volume.

“Nothing worth surfacing” is a successful result.

## D16 — Coarse sensitivity boundary exists before sensitive ingestion

The ordinary Musubi corpus is private internal VedaOps knowledge suitable for every explicitly authorized Musubi model/provider environment.

Secrets, raw customer PII, protected project Evidence, operational databases, and material inappropriate for all authorized Musubi consumers do not enter the ordinary corpus.

Fine-grained ACL machinery remains deferred.

## D17 — Musubi may store accepted VedaOps-level institutional decisions

Some durable decisions have no natural single-project home.

Musubi may be the authoritative record of such a decision after CHAZ makes it.

Musubi itself does not create human/Product authority, and any binding consequence inside a project must be recorded through that project's native process before it is project instruction.

## D18 — Musubi must earn its maintenance cost

The initial Product hypothesis must be tested against a capable-model baseline with project-native docs and read-only project access.

If maintained Musubi knowledge does not materially improve continuity, cross-project reasoning, decision quality, or reconstruction cost after maintenance burden is counted, shrink the Product.
