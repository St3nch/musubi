# Musubi Prototype Evaluation

## Purpose

Musubi must prove that maintained institutional memory adds value beyond a capable LLM with good project documentation and live source access.

The evaluation should therefore compare two conditions using the same model, same source access, and same task budget.

## Baseline

```text
fresh LLM
+ portfolio index
+ text search
+ read-only project repositories / governed native sources
```

## Musubi condition

```text
same fresh LLM
+ same portfolio index
+ curated Musubi institutional knowledge
+ same text search
+ same read-only project repositories / governed native sources
```

## Questions that should favor Musubi if the Product is real

Examples:

1. What lessons from existing projects might help Discrepancy Desk without overriding Desk authority?
2. Which old VedaOps ideas may deserve reassessment because their original blocking conditions changed?
3. Which attractive ideas have already been rejected or deferred, and are the original reasons still valid?
4. What recurring mistakes or design traps appear across multiple projects?
5. What important relationship exists between projects that no individual repository naturally owns?
6. Is there any opportunity worth CHAZ's attention now?
7. What should VedaOps deliberately not do right now?
8. Which current suggestion is mostly a repetition of an older Musubi hypothesis rather than independent evidence?
9. What institutional knowledge requires live verification before it could support an actionable recommendation?
10. Is there nothing worth surfacing right now?

## Failure taxonomy

Evaluate separately:

- wrong retrieval;
- missing retrieval;
- stale institutional knowledge;
- unavailable native source;
- fact/inference confusion;
- reasoning failure despite correct retrieval;
- repeated idea / confirmation-loop failure;
- overgeneralized lesson;
- hallucinated approval or authorization;
- suggestion spam / attention burden;
- unsafe project-action language despite no project-write capability.

## Maintenance economics

Track the human cost of:

- reviewing proposed Musubi mutations;
- correcting stale or weak knowledge;
- pruning low-value ideas;
- maintaining authority pointers;
- evaluating suggestions.

Compare that cost with:

- reconnect time saved;
- repeated explanations avoided;
- bad ideas suppressed;
- useful opportunities found;
- decision quality improved.

## Kill criteria

Radically shrink or abandon the separate Musubi Product hypothesis if:

- Musubi answers mostly restate what the baseline finds just as effectively;
- durable notes rarely change a decision or prevent repeated work;
- maintenance/review cost consumes the savings;
- suggestions become an attention tax;
- shadow-summary behavior emerges despite the project-read-only boundary;
- project-native documentation decays because people rely on Musubi instead;
- durable Musubi inference repeatedly returns as fake independent evidence.

## Promotion criteria

Expand beyond the minimum only after repeated evidence that Musubi:

- recovers institutional reasons the baseline misses;
- identifies useful cross-project connections that survive native verification;
- recognizes changed reassessment conditions;
- suppresses repeatedly attractive but disproven ideas;
- materially reduces CHAZ's reconstruction burden;
- preserves value across fresh sessions or replacement models.

Only after demonstrated retrieval pressure should the project reconsider stronger indexing, vectors, graphs, federation, automation, or proactive institutional radar.
